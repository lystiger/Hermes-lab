# Console visual bugs and broken states

Static code review only. Conditions below are confirmed by code; actual occurrence, viewport appearance, network behavior and backend data are unconfirmed without running the console. No tests or project checks were run.

## Job monitoring and review

- **Dashboard can falsely report no attention or zero reviews.** `console/src/routes/index.tsx:32` reads only `const { reviews } = useReviews();`, then lines 38–40 build attention and `openReviews` from that array. `console/src/api/hooks.ts:256` supplies `reviews: data ?? []`. While loading or after an initial failure, review items disappear and, when telemetry exists, `TO REVIEW` is zero; a failed refresh also leaves old reviews without a stale warning. The empty attention message can say “Nothing needs you right now.”
- **Dashboard metrics can silently go stale.** `console/src/routes/index.tsx:33` takes telemetry error but not stale status; line 68 shows an error only for `telemetryError && !telemetry`. `console/src/api/hooks.ts:103-106` retains prior data on failure. A failed refresh therefore leaves the old header counts with no error. Capacity is similarly read as only `const { capacity } = useCapacityTelemetry();` at line 34, so token failure or stale data is not identified.
- **Floor hides failed refreshes.** `console/src/routes/floor.tsx:21` ignores the jobs stale flag, and line 41 renders an error only for `error && jobs.length === 0`; line 43 keeps rendering the old jobs. A failed refresh after a successful empty list also suppresses the empty message at line 42. Individual job phases have the same problem: line 77 tests `error && !detail`, while lines 80–82 continue to render retained detail. A timestamp alone does not identify a failed refresh. The resource retention is documented in `console/src/api/hooks.ts:103-106`.
- **Job trace has no loading indicator.** `console/src/features/jobs/JobDetailView.tsx:160` shows “No events recorded” only when `!durable.loading`, while lines 157–164 render an error or rows and contain no loading state. When durable history is loading and the live buffer is empty, the trace section is blank.
- **Queue repeats its loading message.** `console/src/routes/queue.tsx:42` renders `LoadingState` when jobs are loading and empty; `console/src/features/jobs/MissionBoard.tsx:74` renders the same state for the same condition inside the board.
- **Recoverable jobs can display stale rows under a full error.** `console/src/routes/queue.tsx:79` renders `{error && <ErrorState ... />}` followed by `jobs.map(...)` at line 81. `console/src/api/hooks.ts:319` exposes `stale`, but the component does not use it. A failed refresh retains rows without identifying them as stale.

## Other views and interaction

- **Usage header hides capacity failures and stale totals.** `console/src/routes/usage.tsx:77-80` uses capacity telemetry, and lines 90–94 render its totals; lines 103–106 only report agent-limit errors. A capacity load failure appears as dashes, and a failed refresh can leave old totals without a stale notice. `console/src/api/hooks.ts:227-234` exposes capacity loading, error, stale and retry.
- **Settings silently shows empty sections on load or failure.** `console/src/routes/settings.tsx:16-17` reads only `agents`, `settings` and `updatedAt`; lines 30 and 70 map those arrays without loading, error or empty states. `console/src/api/hooks.ts:330` defaults settings to `{ runtime: [], policy: [] }`. Failed refreshes can also show retained data without a stale warning.
- **Settings operator rows are mouse-only controls.** `console/src/routes/settings.tsx:71-74` uses a clickable `<div>` with `onClick={() => navigate(...)}` and no link, role, tab stop or keyboard handler. Keyboard users cannot activate these rows.
- **Comms hides conversation navigation on narrow screens.** `console/src/routes/comms.tsx:140` sets the only sidebar to `hidden ... md:flex`; lines 141–148 put select, new, rename and delete actions there. Below the `md` breakpoint these controls have no alternative in this component, so existing chats cannot be selected and a new chat cannot be explicitly started.
- **Comms can replace the selected chat with an older response.** `console/src/routes/comms.tsx:42-45` calls `getConversation(id).then(setSelected)` without guarding request order. Selecting A then B can show A if A finishes last. The same issue can occur when selecting a chat while sending: lines 64–66 and 70–72 set the started chat after asynchronous work, regardless of the current selection. Timing and occurrence are unconfirmed.
- **Comms can lose unsent text on failure.** `console/src/routes/comms.tsx:53-61` clears the draft with `setDraft('')` before conversation creation; the catch at lines 68–74 reports the error but does not restore it. If creation fails, the text has not been submitted and is gone from the composer. A send failure may have persisted the message server-side, as the comment at line 63 says; that behavior is unconfirmed here.
- **Comms initial and chat loads lack loading states.** `console/src/routes/comms.tsx:34-45` starts list, options and conversation requests without loading flags. Lines 187–190 show the new-chat prompt whenever `!selected && !busy`, including while an existing chat is opening; until the list arrives the sidebar receives an empty array.

## Layout, navigation and data boundaries

- **Potential narrow-screen clipping in Settings.** `console/src/routes/settings.tsx:25` and `:65` impose `min-w-[340px]` on both stacked columns. `console/src/components/Layout.tsx:24` uses `overflow-hidden` on the main area. Content narrower than 340px can overflow the available width; actual clipping depends on viewport and scroll-container behavior and is unconfirmed visually.
- **Unknown routes silently redirect to Dashboard.** `console/src/App.tsx:33` uses `<Route path="*" element={<Navigate to="/" replace />} />`. A mistyped or obsolete link gives no not-found indication. No specific internal dead link was confirmed by this review; external URLs depend on runtime data and were not checked.
- **No confirmed missing job-data null check.** `console/src/features/jobs/JobDetailView.tsx:25-39` handles loading, error and absent `job` before accessing fields; `console/src/api/hooks.ts:194-196` also rejects detail for a different ID. This does not prove every nested field is safe for malformed API responses.
