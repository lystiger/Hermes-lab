# Merge and push rights

Scope: static inspection of controller Git paths, agent restrictions, and repository configuration. No Git commands or remote branch-protection queries were run. Likelihood and impact are qualitative and depend on agent access and remote credentials.

## Findings

1. **High likelihood, high impact: agent-side Git ownership is not a universal security boundary.** The goal prompt says never run Git and assigns commits and merges to Hermes (`runtime/hermes_adapter.py:981`). Claude's direct adapter adds named Git mutation denials including merge and push (`runner/agents/claude.py:8`, `runner/agents/claude.py:33`, `runner/agents/claude.py:65`), but these are tool-pattern restrictions, not proof that all equivalent command paths are blocked. Codex's direct adapter forces `workspace-write` (`runner/agents/codex.py:13`, `runner/agents/codex.py:22`); this code does not add a Git command prohibition. Antigravity can receive `dangerously_skip_permissions` (`jobs/job_launcher.py:507`, `runner/agents/antigravity.py:30`). An agent with executable Git or `gh`, network access, and usable credentials may therefore trigger its own push or remote merge subject to its actual sandbox and server rights; this was not tested. Local worktree permissions and tool denials can constrain individual paths, but the prompt alone cannot enforce them. **Smallest guardrail:** run agents without push-capable credentials and enforce repository hosting branch rules; give the controller a separate credential limited to its job branches.

2. **High likelihood, medium impact: integration merges precede final checks and independent review.** Goal tasks are staged, committed and merged into the integration worktree after syntax and role checks (`runtime/hermes_adapter.py:1415`, `runtime/hermes_adapter.py:1429`, `runtime/hermes_adapter.py:610`, `runtime/hermes_adapter.py:641`, `runtime/hermes_adapter.py:658`). A repository lock and execution fences protect consistency, and conflicts abort (`runtime/hermes_adapter.py:620`, `runtime/hermes_adapter.py:628`, `runtime/hermes_adapter.py:653`, `runtime/hermes_adapter.py:660`). The sprint controller also commits and merges mutable phases before finalization (`runner/run-hermes-sprint.py:1463`, `runner/run-hermes-sprint.py:1477`, `runner/run-hermes-sprint.py:1490`). These are local integration merges, not merges into main. **Smallest guardrail:** explicitly label integration as unverified and prohibit deployment or main-branch use until final verification passes.

3. **Medium likelihood, high impact: push does not require CI green or an independently proven agent verdict.** For completed goal-planned jobs, the launcher invokes finalization (`jobs/job_launcher.py:95`); unless `HERMES_AUTO_PR=0`, `gh` is missing, or origin is missing, the finalizer pushes the integration branch and opens a PR against main (`jobs/job_finalizer.py:61`, `jobs/job_finalizer.py:67`, `jobs/job_finalizer.py:72`, `jobs/job_finalizer.py:143`). It also pushes deletion of old integration branches only after an ancestry check and successful local deletion (`jobs/job_finalizer.py:127`, `jobs/job_finalizer.py:133`, `jobs/job_finalizer.py:138`). Finalization itself does not check CI or require a verifier verdict; the PR summary allows no verdict (`jobs/job_finalizer.py:31`, `jobs/job_finalizer.py:49`). The normal goal adapter gates completion on configured verification commands or `hermes.json` checks, failing closed if none exist except dry runs (`jobs/job_launcher.py:512`, `runtime/hermes_adapter.py:1802`, `runtime/hermes_adapter.py:1806`, `runtime/hermes_adapter.py:1875`, `runtime/engine.py:769`). Those checks are read from the integration worktree, so a job can change them (`runtime/hermes_adapter.py:1803`). The generic engine also has a default verifier that only requires completed tasks (`runtime/engine.py:106`, `runtime/verification.py:135`). Scheduler independence is a preference with fallback, not a requirement (`runtime/scheduler.py:330`). An explicit failed/fail task verdict fails that task (`runtime/hermes_adapter.py:1488`); Codex verifier/security output requires an explicit recognized verdict (`runner/agents/codex.py:50`, `runner/agents/codex.py:54`), but other paths do not universally treat missing or UNPROVEN as failure (`runtime/hermes_adapter.py:1373`, `runtime/hermes_adapter.py:1488`). Sprint finalization blocks an explicit `failed` read-only verdict and requires its verification or tests to pass (`runner/run-hermes-sprint.py:2295`). This does not establish a universal FAIL/UNPROVEN block or CI-green gate. **Smallest guardrail:** before push, require a separate actor's explicit PASS and trusted check results for the exact integration commit; treat missing, FAIL and UNPROVEN as blocking. Require CI and review on the host before merging main.

4. **Unknown likelihood, high impact: remote branch protection is unproven.** The finalizer states Hermes opens a PR for human review and does not merge it (`jobs/job_finalizer.py:1`); the inspected controller paths merge locally and push branches, with no controller PR-merge operation found. Repository search found `.github/workflows/tests.yml`, but no checked-in branch-protection configuration or CODEOWNERS. Repository contents cannot establish GitHub rulesets, required checks, bypass rights, or credentials; remote settings were not queried. **Smallest guardrail:** verify and enforce protected main with required CI, independent approval, and no agent-credential bypass; retain human control of production deployment.
