# Prompt injection from repository content

Scope: static inspection of prompt construction and execution paths. No malicious payload was executed. Likelihood and impact below are estimates conditional on an attacker controlling content an agent reads, not measurements of exploitation.

## Findings

### High likelihood / high impact: repository content can influence planning and execution

- `runtime/planning/reconnaissance.py:192-205` walks target files; `:252-258` gives root `AGENTS.md` a 100-point priority and recognizes project skills. `:268-274` reads file contents, and `:308-337` selects ranked files and copies their first 1,500 characters into evidence. Defaults are 20 files and 50,000 characters (`runtime/limits.py:15-17`); the renderer separately defaults to 40,000 characters (`runtime/planning/reconnaissance.py:105-106`). These bounds limit volume, not instructions.
- `runtime/planning/reconnaissance.py:131-140` inserts excerpts inside Markdown code fences without escaping embedded fences. A malicious excerpt can close the fence and impersonate a prompt section. Paths, reasons, contracts and test names are also interpolated as Markdown (`:121-135`). The planner inserts this rendering alongside the goal, constraints and output contract (`runtime/planning/planner.py:301-326`), then sends it to the configured model (`:135-145`). The heuristic fallback is a different path (`:146-159`).
- Model output becomes `PlannedTask.description` and then `TaskNode.description` (`runtime/planning/contracts.py:45-49,62-83`). Validation checks structure, capabilities, references and verification presence, but does not establish that a description is authorized by the user (`runtime/planning/validator.py:57-124`). The worker uses that description as its base prompt (`runtime/hermes_adapter.py:1028-1035,1060-1069`). Separately, agents can read repository files during their work; instructions in those files can influence them directly. A malicious file can ask the agent to run a new skip-permissions process, write outside the worktree, or transmit environment values. This is an instruction path, not proof the model will comply or that the requested operation will succeed.
- Smallest guardrail: treat repository content as untrusted data in planner and worker instructions, encode excerpts so embedded delimiters cannot impersonate sections, and require review of generated plans before execution for untrusted repositories. This reduces instruction confusion but cannot enforce behavior; enforce filesystem, network and credential limits outside the model.

### High likelihood / high impact: observations and task context can carry instructions across agents

- `runtime/engine.py:645-660` registers execution observations including their content and metadata. `runtime/hermes_adapter.py:1633-1667` collects same-job observations from the task, fallback lineage, dependencies or job. `:750-786` places their content verbatim in a labeled continuity section, filtering completion boilerplate but not instruction text. `:969-976` places that section and the base task prompt in the same effective prompt. A previous agent influenced by repository content can therefore relay instructions to later agents. Job goals and sibling task descriptions also appear as text (`:907-935`); sibling descriptions are truncated, not sanitized (`:887-902`).
- Observations marked with `requires_follow_up` can create tasks using `follow_up_task` or observation content, truncated to 500 characters (`runtime/replanning.py:406-438`). This requires an eligible observation kind and the metadata flag; it is not automatic for every observation.
- For verifier/security roles, job diff text is inserted into the prompt, bounded at 30,000 characters, with section markers but no escaping (`runtime/hermes_adapter.py:788-813,1037-1041`). A repository change can embed text resembling those markers. If task metadata specifies `prompt_file`, its contents replace the description, including an absolute path or a relative path resolved against the target repository (`:1028-1035`). The sprint runner likewise reads its resolved prompt file into the effective prompt (`runner/run-hermes-sprint.py:1192-1204`).
- Smallest guardrail: label and encode observations, diffs and repository-derived prompt files as untrusted data; prevent them from creating executable follow-up tasks without an explicit trusted approval. Preserve provenance through each handoff.

## Execution boundaries and limits of the claim

`argv_safe_prompt` only prepends `Instructions:\n` when a prompt starts with `-`; it avoids CLI option parsing and does not filter or neutralize instructions (`runner/agents/base.py:38-47`). Claude, Codex and Antigravity pass its result as one argv element (`runner/agents/claude.py:68-81`, `runner/agents/codex.py:13-26`, `runner/agents/antigravity.py:15-32`); sessionful backends may receive the prompt through metadata instead (`runner/agents/base.py:123-132`). Repository text does not itself add an option to the already constructed argv. Antigravity's skip flag is selected by an option (`runner/agents/antigravity.py:30-31`); Codex's adapter explicitly selects `workspace-write` (`runner/agents/codex.py:22-26`). Whether an agent can launch another process or access outside paths and networks depends on its actual sandbox and permissions, not the text delimiters. The subprocess backend starts the command with a working directory and no explicit environment argument (`runner/backends/subprocess_backend.py:28`), so it inherits the parent environment on that path. Do not infer successful exfiltration from inheritance alone.

The workspace no-git rule is appended as prompt text (`runtime/hermes_adapter.py:978-983`); it is not, by itself, a security boundary. This note does not assess all external enforcement, provider behavior, or other backends. Guardrails should deny unauthorized writes and egress independently of agent compliance, and pass only required secrets to subprocesses.
