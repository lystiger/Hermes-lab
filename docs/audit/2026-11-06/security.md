## High-Severity Findings

### SEC-01: Antigravity Unconfined Execution via `--dangerously-skip-permissions`
When `antigravitySkipPermissions: True` is submitted via `POST /jobs/goal` (`main.py:534, 570`), `jobs/job_launcher.py:507-511` sets `dangerously_skip_permissions: True`, causing `runner/agents/antigravity.py:30-31` to pass `--dangerously-skip-permissions` to `agy`. This flag bypasses all agy interactive permission prompts, workspace trust checks (`trustedWorkspaces`), and allow/deny rules generated by `scoped_antigravity_permissions` (`permissions.py:40-65`). Because `subprocess_backend.py:28` executes commands via `subprocess.Popen` without containerization or namespace isolation, Antigravity executes arbitrary shell commands with standard user privileges, allowing full read and write access across the host filesystem and network. Smallest guardrail: execute agy within an unprivileged OS container or sandbox (such as `bwrap --ro-bind / / --bind <worktree> <worktree>`) that enforces filesystem and network containment regardless of CLI flags.

### SEC-02: Claude Unconfined Shell Execution via `--permission-mode dontAsk`
`runner/agents/claude.py:74-75` launches Claude with `--permission-mode dontAsk` by default, granting unrestricted tool execution. The agent receives the `Bash` tool by default (`claude.py:59`) without an OS sandbox. The only configured boundary is `CLAUDE_GIT_MUTATION_DENIALS` (`claude.py:8-51`) passed to `--disallowedTools`, which checks only CLI tool command string prefixes and is trivially bypassed via shell scripts, Python, or indirect command wrappers. As a result, Claude can execute arbitrary shell commands across the user's home directory, the main repository checkout (`target_repo`), sibling task worktrees, and `target_repo/.git`. Smallest guardrail: run Claude subprocesses inside an OS sandbox (`bwrap`) restricting write access strictly to the assigned worktree.

### SEC-03: Subprocess Environment Credential Inheritance
`runner/backends/subprocess_backend.py:28-29` invokes agent processes with `cwd=cwd` and no explicit `env` parameter, causing subprocesses to inherit the entire environment of the Hermes server process. The legacy launcher similarly passes `env=dict(os.environ)` (`jobs/job_launcher.py:187-200`). This exposes host-wide API keys, cloud tokens, database URLs, and SSH configurations to all agent subprocesses regardless of role or trustworthiness. Smallest guardrail: pass an explicit minimal allowlist of environment variables (e.g., `PATH`, `HOME`, and provider-specific tokens) to agent subprocesses, explicitly stripping server secrets.

### SEC-04: Plaintext Secrets in World-Readable Run Artifacts and Logs
`runner/backends/subprocess_backend.py:38-46, 108-120` captures raw stdout and stderr without redaction, writing logs directly to run directories under `~/hermes-runs`. Log files and directories inherit default process umask (`0755`), leaving them readable by any local user. Inspection of existing run logs revealed plaintext credentials, including an active database connection string with username and password in `/home/lystiger/hermes-runs/run_20261023_170127_3a393724/T2_codex_stderr.log:94` (credential validity unconfirmed). Smallest guardrail: enforce `0700` directory and `0600` file permissions on run directories and scrub recognized credentials before writing logs.

### SEC-05: Unauthenticated HTTP API Control and State Disclosure
The FastAPI application constructed in `main.py:88-95` defines no authentication middleware or security dependencies, explicitly acknowledging unauthenticated access. Any local process or browser site permitted by default CORS origins (`localhost:3000`, `3001`, `5173`) can query active jobs, tasks, runs, and event streams (`main.py:384-484`), launch new jobs (`main.py:540-573`), cancel or resume running jobs (`main.py:494-506, 578-598`), and alter runtime model configuration (`main.py:362-367`). Production network bind address and reverse proxy configuration are unconfirmed. Smallest guardrail: require Bearer token authentication from a local secret file on all API routes and hardcode loopback binding (`127.0.0.1`).

### SEC-06: Prompt Injection via Unescaped Repository Reconnaissance
`runtime/planning/reconnaissance.py:192-337` walks target repository files, giving highest priority to root `AGENTS.md` and reading up to 50,000 characters from ranked files. Excerpts are formatted into Markdown code blocks (`reconnaissance.py:131-140`) without escaping nested backticks or fences. An untrusted repository can embed malicious instructions that break out of markdown fences, masquerade as system prompts, and manipulate `PlannedTask` generation (`runtime/planning/contracts.py:45-49`). Generated task descriptions are executed directly by workers (`runtime/hermes_adapter.py:1028-1069`). Smallest guardrail: enclose repository excerpts in non-colliding boundary tokens, instruct models to treat repository text strictly as untrusted data, and require manual approval of generated plans on untrusted repos.

### SEC-07: Cross-Agent Prompt Injection via Continuity Observations and Diffs
Execution observations registered in `runtime/engine.py:645-660` are collected and interpolated verbatim into downstream agent prompts in `runtime/hermes_adapter.py:750-786, 969-976`. If an agent reads untrusted repository content, it can emit observations containing malicious instructions that downstream agents execute without sanitization. Furthermore, observations flagged with `requires_follow_up` can automatically generate executable follow-up tasks (`runtime/replanning.py:406-438`), and verifier diffs up to 30,000 characters are inserted without delimiter escaping (`hermes_adapter.py:788-813`). Smallest guardrail: mark observations and diffs as untrusted data and require explicit approval before creating executable follow-up tasks.

### SEC-08: Shared Git Hooks and Config Exploitation from Worktrees
While git worktrees isolate working directory files, `.git` points back to `target_repo/.git` (`runtime/hermes_adapter.py:494-541`). Because Claude and Antigravity (with skip-permissions) run without filesystem sandboxes, an agent can modify `target_repo/.git/hooks/*` (e.g., `pre-commit`, `post-commit`) or `target_repo/.git/config`. When the controller subsequently commits or merges integration changes (`hermes_adapter.py:641-659`), it executes those hook scripts with controller privileges. Smallest guardrail: pass `-c core.hooksPath=/dev/null` on all controller git commands and abort if `.git/config` or `.git/hooks` are modified.

### SEC-09: Unenforced Agent-Side Git Mutation and Remote Push Restrictions
Hermes attempts to forbid agent git actions using prompt instructions ("never run git", `runtime/hermes_adapter.py:981`) and Claude CLI tool prefix denylists (`runner/agents/claude.py:8-51`). Prompt instructions are advisory and tool denylists are easily circumvented via shell scripts, Python subprocesses, or raw git binaries. Codex has no git command denial in its adapter (`runner/agents/codex.py:22`), and Antigravity with skip-permissions has unrestricted shell execution. Any agent with access to git credentials in its environment can push commits or merge branches directly to remote hosts (actual network egress and remote git push capability under agent sandboxes are unconfirmed). Smallest guardrail: strip git credentials from agent execution environments and enforce remote repository branch protection rules on Git host.

### SEC-10: Automated Push and PR Finalization Without Verifier PASS or CI Gate
Upon goal job completion, `jobs/job_finalizer.py:61-72` automatically pushes the integration branch and opens a pull request against main. Finalization does not verify remote CI status or enforce an independent agent PASS verdict (`job_finalizer.py:31, 49`). Furthermore, verification commands in `runtime/hermes_adapter.py:1802-1806` are read from the integration worktree, allowing jobs to alter their own test suites. Fallback verifiers in the engine only check task completion (`runtime/engine.py:106`), and missing or UNPROVEN verdicts do not universally block integration (`hermes_adapter.py:1373, 1488`). Smallest guardrail: require an independent verifier PASS and green CI status before pushing branches or opening PRs; treat UNPROVEN and FAIL as blocking.

### SEC-11: Arbitrary Command Grants in `allowedCommands` API Parameter
The `POST /jobs/goal` schema accepts `allowedCommands` as a list of up to 50 strings (`main.py:526, 566`). The endpoint performs no character validation, command allowlisting, or sanitization. Callers can supply arbitrary interpreters (`python`, `bash`, `sh`, `uv`) or wildcard characters (`*`), which are interpolated directly into agy allow rules (`runner/agents/permissions.py:59`). Granting an interpreter effectively grants arbitrary shell execution. Smallest guardrail: validate `allowedCommands` via Pydantic regex rejecting interpreters (`sh`, `bash`, `python`, `uv`), wildcards (`*`), and shell operators.

### SEC-12: Prefix vs. Exact Match Discrepancy in `allowedCommands` Enforcement
Hermes code and documentation assert that `allowedCommands` represents exact declarations (`main.py:525`, `runner/README.md:14-16`). However, the embedded help in the agy 1.5.2 binary documents prefix matching (`command(<prefix>)`) and wildcard syntax (`command(*)`). If agy matches prefixes, granting `command(git)` or `command(pytest)` allows arbitrary subcommands and arguments (e.g., `git push` or `pytest --import-mode=...`). Real agy command matcher behavior (exact vs prefix and `command(*)` wildcard grant) is unconfirmed without live execution. Smallest guardrail: add integration test pinning agy matcher behavior; enforce strict command token validation in Hermes before writing permissions.

### SEC-13: Unchecked Main Repository Checkout (`target_repo`) Integrity
The Hermes controller isolates agent execution in worktrees, but agent processes running without OS sandboxes have full filesystem access to the main checkout (`target_repo`). Following task completion, `runtime/hermes_adapter.py:590-600, 1342-1420` inspects and validates changes only within the task worktree and integration worktree. If an agent writes or modifies files directly in `target_repo`, the controller does not detect the change, leading to silent repository tampering. Smallest guardrail: check `git status --porcelain` on `target_repo` before and after each task run, aborting the task if any change is detected.

### SEC-14: Directory Traversal Risk via Unsanitized Planner `task_id`
When creating task worktrees, `runtime/hermes_adapter.py:1302, 1306` constructs the worktree directory as `worktree_root / wt_name`, where `wt_name` derives directly from `task.task_id`. The planner task validator (`runtime/planning/validator.py:71-77`) only verifies that task IDs are unique and non-empty. If a model-generated plan includes path traversal characters (`..` or `/`), the worktree could be created outside `worktree_root` (whether Git branch ref rules reject all directory traversal forms is unconfirmed). Smallest guardrail: validate `task_id` with regex `^[A-Za-z0-9_-]+$` and assert `path.is_relative_to(worktree_root)` before creating worktrees.
